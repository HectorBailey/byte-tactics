# Source cleanup roadmap

All 3,267 functions match and `tools/place.py` rebuilds the shipped exe
(MD5 `8e74a1dffa1f5988624c52048f5b20cd`). This page is the plan for making the
source read like source. It sits beside `docs/tidy-up.md`, which covers folders,
names and shared types in detail; this page orders the whole job, adds the work
that page leaves out (comments, casts), and records what the pilots showed.

Numbers were measured on 2026-10-06 on `main` before PR #5775, and are kept as
that snapshot; see "Already done" for what has landed since.

## Where things stand

| --- | --- | --- |

| Duplicate type definitions | `Unit` is defined in 281 files | one partial view per file |
| One function per file | 2,775 files (2,483 after the merges since) | `docs/tidy-up.md` phase 3 |

Already done: files sorted into folders, 313 classes named, ozgb's class and
module gathering (#5773, #5774, #5775), redundant casts in 49 files (#5776,

(#6025), and `ready`/`blocked` labels that order the `cleanup` issues (#6020).

## What limits the work

Read this before picking a task. These are why the order below is not the
obvious one.

1. **The compiler state decides matches.** MSVC 5's register allocation depends
   on a symbol counter that grows with every declaration before a function
   (`docs/c2-regalloc.md`). A type costs 7 ids, a member function 1 plus 1 per
   parameter, a forward declaration 1. **Data members cost nothing.** So adding or
   renaming fields inside a file is safe; adding types, member functions or forward
   declarations, or including a big shared header, can break matches. Nine files
   only match with `include/ta_types.h` at its exact current size.
2. **Casts are sometimes load-bearing.** In `side_data_431a60.cpp` a
   `TdfRecord*` local in place of the cast drops the function to 89%. A cast can only come out if the whole file
   still matches afterwards.
3. **The gate is the check, not the editor.** Every change must keep every
   function `MATCH` (`tools/checkall.py`) and the whole build at the shipped MD5
   (`tools/place.py`, about 15 minutes). Per-function matches alone are strong
   evidence but do not cover linking.
4. **The compiler runs under Wine.** It is a 1997 Win32 binary;
   `tools/setup_toolchain.sh` sets it up. A full `place.py` build compiles
   every changed file, so run one at a time on a small machine.
5. **Other people change the same files.** Gathering PRs merge and delete source
   files. Any change that touches thousands of files has to be a script that can
   be re-run after a rebase, not a hand edit.

## What the pilots showed

- Two Haiku agents given one exact recipe each (retype the variable, delete the
  casts, run `check.py`, undo on failure) changed 5 files correctly and left 2
  alone because the retype was not possible. Re-running the checks independently
  found no errors.
- Most casts were already redundant: of the 173 removed so far, nearly all were
  `((T*)x)->` where `x` was already `T*`. That is a try-and-verify loop, so a script
  is better than an agent for it.
- The remaining casts are real: the variable is `void*` or its class is declared
  too late. Those need the types to be fixed first, not more cleanup.
- The script's yield is low outside a few files (11 casts from the first 45
  files; the heavy `orders/`, `map/`, `game/` files are better). It averages about
  4 minutes per file when a file has many groups and nothing removes.
- Always re-verify after killing a run: two files were left half-edited and
  non-matching when a job was stopped.

## The phases

Each phase lists its goal, how, the gate, who does it, and when it is done.

### Phase 0: keep the gate working

- Goal: any change can be checked against the shipped MD5 locally and in CI,
  including pull requests from forks (#6026: a maintainer approves each run).
- Do: keep `place.py` working locally (done), keep CI green, add a script that
  prints the table above so progress can be read off.
- Done when: the table is regenerated by one command. Done (#6249): `uv run
  tools/cleanup_progress.py` prints it, and its rows follow the later phases'
  work (matching notes, casts, byte-offset access), not only the starting
  problems.

### Phase 1: remove the matching notes (low risk, large gain)

- Decided: the notes are deleted, not moved to `docs/`. Every function matches,
  so the record of how each match was found (scores, attempts, who tried what) is
  history, and git keeps it. What a reader editing the code needs stays in the
  source: the credit line, a description of what the code does, and a one-line
  comment wherever the notes said a construct must stay as it is for the match.
- How: a model pass per file, because descriptions and notes share paragraphs
  and no keyword rule separates them. A script checks that only full-line
  comments changed and that credit, `// FUNCTION:`, `// GLOBAL:` and
  `// FLAGS:` lines survive.
- Gate: that script, then `place.py` MD5.
- Done when: no file opens with matching history, and `AGENTS.md` no longer
  asks for notes in the source.

### Phase 2: redundant casts, inside each file (running)

- Goal: remove every cast that does not change the compiled code.
- How: `trycasts.py` tries each cast group per file and keeps it only if every
  function in the file still matches. The first 19 files are in PR #5776; 137 more
  are queued, most yield is expected in `orders/`, `map/`, `game/`.
- Gate: `checkall` on each file, then `place.py` before merging.
- Who: the script, one process at a time. Agents are not needed.
- Done when: the script finds nothing more to remove. The leftovers are phase 3's
  input: a list of casts that need a type fixed first.

### Phase 3: translation units and per-unit headers, leaf classes first

The aim is source as close as possible to what Cavedog had in 1997, so this phase
follows the evidence, not the file count. Cavedog had one `.cpp` per translation
unit and headers per class or subsystem, each included in some order; they did not
have one header of every type. What can be recovered, strongest first:

| Layer | Confidence | Evidence |
| --- | --- | --- |
| Which functions shared a `.cpp` | high | the linker kept each unit's functions together in source order; four modules name their file in an assertion (`frontend.cpp`, `multi.cpp`, `endgame.cpp`, `wargame.cpp`) |
| Layouts, offsets, hierarchy, inlining | certain | the exe |
| Which headers a unit included, in what order | measurable | the compiler's symbol counter (`docs/c2-regalloc.md`) shows how many declarations preceded a function |
| Names | medium to low | strings, vtables, assertion text, TDF key names (`GetFieldInt("energycolor")` stored in `energyColor`) |
| Formatting, comments, local names | unknowable | no evidence survives |

- Goal: each translation unit is one file with the header set it plausibly had;
  types are defined once in the header that owns them, not once per file.
- Why it is hard: see limits 1 and 3. A header changes the symbol counter for every
  file that includes it; `docs/tidy-up.md` estimates about 3% of functions change.
  A single header of every type is the wrong shape: it lands 2,000 to 12,000 ids
  away from the windows that functions need (`docs/c2-regalloc.md`).
- How, in this order:
  1. Translation units: ozgb's class and module gathering (#5773 to #5775), then
     the `cleanup` issues from #5778 on, one module at a time (`AGENTS.md`,
     section 6).
  2. Leaf library classes first: `HapiBank` (#6024), then `TdfFile` and
     `TdfRecord` (#6025), all in `util/`. Each is self-contained, widely used, and exactly where the casts
     that could not be removed remain. One header each, included by the files that
     use it. Measure with `tools/stateprobe.py` which functions change when it is
     force-included, so the fallout rate is known cheaply before the big types.
  3. Name members from evidence (TDF keys, COB script names, strings), then
     `Unit` and `Game` last, because they touch every file.
- Gate: `stateprobe.py` before, `checkall` and `place.py` after, per type; one type
  per PR.
- Who: a strong model designs; small models only for fully specified
  mechanical steps with a pass/fail command.
- Done when: every translation unit is one file, the leaf classes have headers, and
  the number of definitions of `Unit` has fallen from 281 to one plus documented
  exceptions.
- Limit: names will be plausible, not original, except where strings give them.
  Do not present a guess as a recovered name.

### Phase 4: real member names, then offset casts

Needs phase 3, because a name only means something once there is one struct.

- Goal: `field_<offset>` and `unknown_<offset>` replaced by names, and
  `*(T*)(p + off)` replaced by member access.
- How: name members from evidence (strings, callers, COB script fields, other
  names already in the shared header), starting with the 50 most used of the 574.
  A script then rewrites the offset casts that land on a named member.
- Gate: `checkall` on every file touched, `place.py` per batch.
- Who: naming by a strong model in batches of one struct; the offset rewrite by
  script; small models can apply a batch of renames from a reviewed table.
- Done when: fewer than 100 `field_` names remain and byte-offset casts are down
  to cases with no struct.

### Phase 5: names for the remaining functions and globals

- Goal: no `FUN_`/`DAT_` names left where a name can be earned.
- How: the existing flow, `tools/rename.py` with a pairs file, module by module
  (`docs/tidy-up.md`, "Renaming a module"). 947 functions and 737 globals.
- Gate: what `rename.py` already runs (all functions, MD5 both ways, `linkcmp`).
- Who: a model proposes names from the evidence; a person reviews the pairs file;
  the tool applies it.
- Done when: placeholders left are the ones with no evidence, listed in a doc.

### Phase 6: one file per module

Continues from #5773 to #5775 in the `cleanup` issues: classes first, then
modules. Run phase 2 only after a module's gather has merged, since gathering
moves code between files.

### Phase 7: function boundaries and structure (audit first)

- The function boundaries are fixed by the exe, so they cannot be wrong in a
  matching build. What can be wrong is which module a function is placed in
  (`data/modules.csv`, inferred from address order and strings) and long functions
  that are really several helpers the compiler inlined.
- Do: audit 20 of the longest functions (84 files are over 12 KB) and sort them
  into "inlined helpers that can be pulled out" and "genuinely long".
- Gate: pulling a helper out has to match; use `inline` and check with
  `check.py`.
- Done when: the audit is written up and a short list of extractions is queued.

## Order and dependencies

```
Phase 0 (gate) ──┬─ Phase 1 (notes) ──────────────┐
                 ├─ Phase 2 (casts, in file) ─────┼─► Phase 3 (shared types)
                 └─ Phase 6 (cleanup issues) ─────┘          │
                                                    Phase 4 (members, offset casts)
                                                             │
                                                    Phase 5 (names)   Phase 7 (audit)
```

1 and 2 are independent and safe now. 3 needs the file layout to settle (phase 6),
because gathering files changes which views exist. 4 and 5 need 3.

## Working rules

- One kind of change per PR, with the check results in the body. PR #5776 is the
  model.
- Script anything that touches more than about 20 files, and make it re-runnable.
- Give a small model a task only if it has one recipe, one file set, a
  pass/fail command and an instruction to undo on failure. Then verify its result
  yourself before merging.
- Never leave a worktree edited and unchecked: after stopping any run, run
  `checkall` on every modified file and revert what fails.
- Keep `AGENTS.md` style: no em dashes, commit subjects `<Type>: <Subject>` under
  50 characters, no attribution lines.

## Decisions

1. Matching notes: deleted, keeping descriptions and load-bearing constraints in
   the source (phase 1).
2. Pull requests go upstream as they are; there is no separate fork to carry
   phases 1 and 3 to 5 first.
3. Open: how much of phase 3 to attempt, the top 10 types or all of them. The 3%
   fallout is a guess until one of the big types is done.
