# AI player state, production, squads and target selection

[Systems manual](../index.md) | [Completion tracker](../../doc-writeup-roadmap.md)

Module group: `ai/ai_player`, 115 annotated entries in the address interval `0x406c90` to before `0x40d5e0`. The implementation comprises [ai_player.cpp](../../../src/ai/ai_player.cpp), ten retained companion translation units and [player_ai.cpp](../../../src/ai/player_ai.cpp). This reference covers production policy, placement, enemy caches, automatic targeting, retaliation, squad assignment and every timer family. It also accounts for the container specializations in this address range.

## 1. Two state objects and their execution order

SquadManager is the per-player group/timer controller. PlayerAI is a separate indexed object in g_playerAI with caches, definition tables, placement state and an estimated base position. Human players also use automatic weapon acquisition through these services. Calling everything in this module computer-only would conceal that dependency.

The [player lifecycle and tick caller](../../../src/game/players_464290.cpp), particularly InitPlayerSlot, InitPlayers and UpdatePlayers, creates the objects, loads policy scripts and invokes updates. Initialization creates squads, then a SquadManager and PlayerAI unless the player is both active and type 3. CreatePlayerAI (`0x40b320`) allocates the indexed object and immediately computes base weights. DestroyPlayerAI (`0x40b390`) deletes it and clears its slot. These functions do not replace an existing nonnull slot defensively.

PlayerAI construction (`0x409160`) retains owner/index, initializes cell-center metadata to half the map tile dimensions, zeros its vector-like positions and search/tick fields, randomizes placement grids and sizes its tables to unitDefCount. InitUnitTables (`0x409470`) gives base-centroid weights 40 for immobile definitions plus 20 when their build-option pointer is nonnull. It resets counts, sets production multipliers to 100, clears locks and sets limits to -1, the unlimited sentinel.

UpdatePlayers first runs path searches. For each eligible active player it calls SquadManager::TickIfActive, then UpdatePlayerAI, then updates unit sight. Thus squad decisions can use the preceding cache refresh, and the refresh can precede this tick's new sight calculation. The reference does not assume all these views are synchronously rebuilt before every weapon decision.

UpdatePlayerAI (`0x40b2c0`) checks for a nonnull state and refreshes only when gameTick is at least lastTick plus 30. It records the current tick, then recomputes base scores with probability 1/30. UpdateEveryThirtyTicks (`0x40ad20`) implements the same periodic policy on an existing object. Neither catches up with repeated refreshes after a large tick jump. At the game's 30 ticks per second, the eligibility interval is one simulation second, while the random score update has no fixed deadline.

## 2. Unit caches, counts and base estimate

RefreshUnitLists (`0x40aa40`) is retained in [player_ai.cpp](../../../src/ai/player_ai.cpp). It clears visible enemies, known enemies and friendly factory/service candidates, resets builder/special counters and zeros the signed-short type counts. It scans global unit slots from units+1 through unitsEnd inclusive. A qualifying unit has runtime bit 0x10000000 set and bit 0x4000 clear.

For nonallied owners, visible membership requires IsUnitVisibleToPlayer and runtime bit 0x8000 clear. Known membership instead requires runtime bit 0x100; this branch does not independently demand current visibility. Allied foreign units enter neither the enemy caches nor the owner's production counts. Own units count only when buildLeft is exactly zero.

The builder counter tests the definition field at +0x156, which the shared definition declares as the build-option ID pointer. A local view calls it builder, but the implemented count is of completed units with that pointer, not a fresh test of the FBI builder flag. Factory/service cache membership requires definition flags1 bits 6 and 9 and activation bit 1. The special-presence flag requires flags1 bit 10 plus activation bit 1. Those predicates remain explicit here because a provisional local name is insufficient evidence for a broader design interpretation.

Own completed units contribute to a floating-point weighted mean of position using the signed-byte centroid weight table. The calculation converts fixed positions to world units, averages and converts back to 16.16. A zero total leaves the estimate at zero. GetBasePosition (`0x40ba80`) simply copies this estimate; it does not locate an actual commander or factory each time. GetMirroredBasePosition (`0x40bab0`) subtracts X and Z from mapWidthWorld in fixed units, sets Y zero and ignores its extra argument. Using width for Z as well as X is a literal implementation detail on rectangular maps.

Counts are completed-unit snapshots, not reservations for work already queued. GetUnitCount (`0x40c200`) masks the requested index to 16 bits and sign-extends the stored short. GetBuilderCount (`0x40c230`) and HasSpecialUnit (`0x40c4f0`) return cached values. These leaf accessors assume valid player state and indices.

## 3. Policy commands, limits and script loading

RegisterAICommands (`0x406f00`) registers plan, weight and limit with command flags 8. CmdPlan (`0x406c90`) first disables subsequent AI commands. It enables them when a supplied difficulty name matches difficulty 0/1/2, or when argument 1 equals any. The any test repeatedly reads argument 1, even while the difficulty tests iterate later arguments. With no arguments the gate remains off. EnableAICommands (`0x406da0`) explicitly turns it on.

CmdWeight (`0x406db0`) reads a type/category bitset and a float multiplier, defaulting to zero, and applies it to every player whose AI/controller pointer is nonnull. CmdLimit (`0x406e40`) reads the same selection and an integer defaulting to zero, but restricts recipients to active type-2 players. Both do nothing while the global command gate is off. The selector parser also returns a value passed as the lock argument, so selection specificity can affect subsequent mutability through that existing parser contract.

ScaleUnitWeights (`0x409dc0`) visits selected definition IDs 1 through unitDefCount-1. If the multiplier lock is zero, it multiplies the current unsigned-byte percentage, truncates and clamps to 0..100. A nonzero lock argument then makes the entry sticky. SetUnitLimits (`0x409e90`) similarly updates unlocked integer limits and optionally locks them. Limits do not remove units or cancel orders. IsUnderLimit (`0x409f20`) accepts valid IDs only; -1 means unlimited, otherwise the supplied count must be strictly less than the limit. IsCountBelowAiLimit (`0x406ee0`) forwards that result. Zero blocks further selection; other negative limits besides -1 do not acquire unlimited semantics.

The [player-side LoadDefaultAIScript](../../../src/game/players_464290.cpp) first loads the mission's name-slot-7 file, falling back to ai/default.txt. It executes available text through the command interpreter and frees the loaded buffer. For every active computer player it then invokes both downloadable-definition passes. ParseDownloadableAiWeightScripts (`0x409f80`) enables the global gate, visits flags1 bit-5 definitions whose multiplier lock is not 1, and executes nonempty aiWeight strings. ReparseAiWeightScriptsIfLimitNotSticky (`0x40a040`) repeats the process using the limit lock. Executing one definition's string is not intrinsically confined to that definition or player: the registered commands still select recipients and category sets as described above.

ResetAIPlayers (`0x40a100`) resets unit tables for active type-2 players and reloads policy text. It does not reconstruct every PlayerAI object, rebuild every feature list or reset all squad timers. Profile tokenization is separately documented in [ai_profile](ai-ai-profile.md); command execution and higher-level configuration consumers remain outside this module.

## 4. Definition scores and economic production choice

ComputeBaseWeights (`0x409730`) is in [its retained file](../../../src/ai/ai_player_409730.cpp). It produces a signed-byte tactical rating and three signed-byte production ratings for each nonzero definition ID. These tables have different purposes from centroid weights and script multiplier percentages.

RateWeapons (`0x409520`) starts at 1, or 11 with flags2 bit 4, and for each of three nonempty weapon definitions adds integer damage/40, range/100 and 5. It clamps to -100..100. RateUnitType (`0x4095d0`) starts at 11 for an extractor, otherwise 1, adds 10 for makesMetal and 10 for negative GetEnergyUse, adds positive metalCost*0.01 and energyCost*0.002 through staged integer conversions, then adds the weapon score and clamps. These are heuristic ratings, not damage-per-second simulation or a full construction cost model.

The ordinary production score starts at 1, or 21 with flags2 bit 4. It adds 30 for a builder definition with fewer than three counted units, 50 for net energy production, 50 for extraction, 25 for makesMetal, 40 for flying, 15 for sonar, 5 for radar, and energymake clamped to 0..30. Zero owned units multiply the score by four; one multiplies it by two. Nonnegative minwaterdepth multiplies by three. Above half the unit allowance it adds half the tactical rating. Flags2 bit 8 or flags1 bit 24 force zero; a wind generator is also zeroed when windSpeedMax is below half windSpeedDenominator. The final ordinary score is capped at 100.

The metal-shortage rating is metalCost*(-0.02), plus 25 for makesMetal and 100 for extraction, clamped to 0..100. The energy-shortage rating is energyCost*(-0.0025) minus GetEnergyUse*5, also clamped to 0..100. Positive production therefore offsets cost penalties. Unresolved definition bits remain numbered rather than assigned an invented unit role.

GetBuildRating (`0x40bb00`) returns zero below 50 stored energy or 25 stored metal, and rejects downloadable definitions in game type 1. It computes metal and energy urgency from missing storage, using effective capacity ceilings of 500 metal and 1000 energy. Storage deficits contribute 0.25 per metal and 0.125 per energy; net production below 1 adds 20. Metal income below 3 adds 100, otherwise below 5 adds 20. Energy income below 50 adds 100, otherwise below 200 adds 10.

Metal urgency is clamped first to 0..100. Energy gets the remaining priority by clamping energy urgency minus the metal share to 0..100. Ordinary share is what remains of 100. After the count-limit check, the weighted sum of ordinary/metal/energy ratings is multiplied by the script percentage and divided by 10000 with integer truncation. Tiny positive components can therefore produce a zero result.

ChooseBuildOption (`0x40bdb0`) walks the builder's option IDs, ignoring nonpositive ratings. A running-total random replacement gives each positive option a chance proportional to its rating without constructing a repeated-entry list. Only after choosing does it compare builder and product side strings case-sensitively. A side mismatch returns no choice rather than trying another candidate. The selection does not reserve resources, increment the cached count or prove a placement exists.

## 5. Placement grids, extractors and expanding retries

InitPlacementGrid (`0x40a150`) creates two randomized cell grids. The first has margin 3, X spacing 11..20 and Y spacing 11..13; the second has margin 6, X spacing 14..33 and Y spacing 14..16. Each offset is a random spacing value minus half the spacing. FindRandomPlacementCell uses the first grid for negative minwaterdepth and the second for nonnegative minwaterdepth. This is a depth-field comparison, not a ship class lookup.

BuildFeatureCells (`0x40a7b0`) clears the candidate list and scans every map tile. A feature index below 0xfffb contributes when the feature's float value is nonzero and its 16-bit flags contain 0x200. Each entry records the tile and feature value. Multi-cell feature representations can contribute multiple cells. RebuildFeatureCells (`0x40b370`) explicitly refreshes the cache; the normal 30-tick refresh does not rebuild it.

FindCellNearFeatures (`0x40a260`) returns false for an empty list. It converts the world search center to a footprint-origin-aware tile coordinate, gathers candidates within range squared and uses a heap keyed by negative squared distance to visit nearby entries first. Each candidate is adjusted by half of footprint minus three and tested with CanBuildAt. The candidate must improve GetBuildSiteMetal above the current best, initially zero. After the first success, the search stops when the adjusted squared distance exceeds that first success distance plus 160. The 160 is added to a squared-distance value, not interpreted as another 160 cells of linear radius. Failure leaves the output untouched.

FindRandomPlacementCell (`0x40a5d0`) makes at most 30 attempts. Each creates a random radial offset, converts to a footprint-aware cell and snaps/jitters each coordinate using the chosen grid. It accepts CanPlaceUnitFootprint with occupancy enabled only if the resulting build-site metal is at most twice surfaceMetal times footprint area. This discourages ordinary structures from consuming valuable metal sites. Grid jitter ranges subtract margin and footprint size; this method has no local repair for oversized footprints making that random range nonpositive.

FindBuildPosition (`0x40bfe0`) grows one shared per-player searchRadius by 160 while it is below the larger world-map dimension. It moves the builder's search origin towards the estimated base by at most that radius, using fixed-vector MoveToward/MoveTowards (`0x40beb0` and its inline equivalent). For an extractor, when the mission threshold is less than RandomInt(255), it searches feature cells at four times the radius. Otherwise it uses random placement. On success it converts the chosen cell back to X/Z world position and resets radius to zero; on failure radius persists for later attempts, including attempts by other builders/types.

CellToWorld in this module writes X and Z only. It does not initialize the output Y. Likewise ScoutTimer reads candidate Y in its special range check even if placement failed. Those are source-level initialization limits, not evidence of a well-defined terrain-height result. The subsequent order/placement infrastructure must supply applicable height behavior; this reference does not silently fill in an assignment absent here.

## 6. Squad slots, classification and scheduling

SquadManager construction (`0x408cb0`) retains the player/index, initializes countdown to 30, clears its cursor and nextAction, and creates nine timers. Slot 0 remains null. Every timer retains its group, owner, player index and absolute next tick, initially zero.

| Slot | Timer | Function and main cadence |
| --- | --- | --- |
| 1 | BuildTimer | Idle production/converters, 30 ticks |
| 2 | AssaultTimer | Forms an assault from slot 3, 300 ticks, spatial limit 20000 |
| 3 | EscortTimer | Moves towards slot 2's centroid, 150 ticks |
| 4 | ScoutTimer | Mobile building and base patrol, 90 ticks |
| 5 | SquadTimer | Base/rally group, empty callback |
| 6 | AssaultTimer | Forms an assault from slot 7, 300 ticks, spatial limit 50000 |
| 7 | EscortTimer | Moves towards slot 6's centroid, 150 ticks |
| 8 | SquadScoutTimer | Small patrols or map-edge scouting, 30..929 ticks |
| 9 | SpatialTimer | Samples target areas, 30..179 ticks |

TickTimers (`0x408bf0`) decrements the assignment countdown, resets it to 30 when due, then invokes any due timer once in increasing slot order. TickIfActive (`0x408c40`) performs that work only for active type-2 players, then calls RetargetWeapons with force=1. Other players only receive RetargetWeapons(force=0). The empty base callback does not advance its next tick, so once eligible it remains eligible but has no effect. DeleteTimers (`0x408f10`) deletes every nonnull timer without nulling the entries; callers must not invoke it again on stale pointers.

AssignSquads (`0x408830`) operates on units carrying runtime bit 0x20. It sets one of runtime 0x40000/0x80000 from definition flags2 bit 12, then replaces runtime 0x100000 with 0x200000. It assigns only units whose group is zero. Runtime 0x20000000 takes precedence: such units enter slot 5 if bit 0x80000000 is also set, otherwise slot 1. Remaining builders go to slot 4, flying definitions to slot 8, positive-minwaterdepth definitions to slot 7, and remaining bit-0x80000000 units to slot 3. Existing group assignments persist. There is no automatic initial slot-9 branch in this classifier.

Group::Send delegates to the [squad dispatcher](units-squads.md), which resolves actual orders per unit. GetAveragePosition (`0x407410`) averages whole X/Y/Z coordinates and returns a fixed vector, failing for an empty group. TryGetBaseBuildOrScoutCentroid (`0x4073b0`) tries slots 5, 1 and 4 in that order. CountGroupUnitsInRadius (`0x4074a0`) scans the owner's entire unit range for matching group ID and horizontal distance; it adds no separate ready/liveness condition.

## 7. Factory production, converters and mobile builders

BuildTimer::OnTimer (`0x4086d0`) requires runtime bits 0x20000000 and 0x10000000 and rejects bit 0x4000. For makesMetal definitions it compares stored energy against twice the field at +0x98 of the owner economy. Below or equal to that threshold it switches the unit off. Above it, positive net energy and a nonzero RandomInt(5) switch it on. Failure of that random/net test does not explicitly switch an already active unit off. UpdateConverter (`0x408670`) exposes the same converter policy independently.

For other eligible units, a nonempty build-option count and no primary order list allow ChooseBuildOption followed by QueueBuildOrder for one product. TryIssueIdleFactoryBuildOrder (`0x408620` in [its file](../../../src/ai/ai_player_408620.cpp)) exposes the idle-list/choose/queue portion. These calls initiate the established production pipeline; the AI does not render its own scaffold, wireframe or emerging hull. Those visuals consume construction state in the model/rendering systems.

ScoutTimer::OnTimer (`0x408100` in [its file](../../../src/ai/ai_player_408100.cpp)) handles group 4. Its first pass permits a unit with build options and no order carrying flag 8. A flags2-bit-12 unit additionally requires fewer than five cached builders and gameTick at least manager.nextAction. It chooses a product, searches placement and, for that special definition class, rejects a position beyond one third of mapPixelWidth plus mapPixelHeight from base. The identical range comparison appears twice. A successful position issues mode 14 with product ID and count 1. This is not a direct unit spawn or free resource grant.

The second pass handles absent orders or order flag 0x4000. Bit-12 units participate only when at least five builders exist. They move to a point mirrored through the base relative to themselves, followed by an appended patrol back to base. If their base displacement exceeds 640 world units, a random 640-unit direction substitutes for the displacement. Other builders patrol towards base; within 320 units the vector is extended to 320, with a random direction if closer than 16. A live build order can therefore suppress this fallback through the order flags rather than a separate AI busy field.

## 8. Assaults, escorts and aircraft patrols

AssaultTimer starts with minimum 3, maximum 6 and attacking false (`0x407930`). RebalanceAssaultGroupByCentroid (`0x407560`) first takes one unit from its paired reserve if empty. While the assault has more than one unit, it sends the farthest member back when squared distance from its whole-coordinate centroid is at least limit times group size. It then gathers reserve units nearer than that threshold into a temporary list and transfers them into the assault. This is a spatial grouping heuristic, with a growing radius proportional to the square root of size, rather than fixed six-unit squads.

The removal loop calls SetUnitSquad on a vector element and then dereferences the old iterator again to subtract its position. The [group implementation](units-squads.md) mutates membership; the literal ordering warrants care and is not rewritten here as a guaranteed stable saved-unit reference.

OnTimer (`0x4077e0`) rebalances, then rallies groups of at most three, or a group that has not begun attacking and still has fewer than six, if a base/build/scout centroid exists. Rally uses mode 2 with radius argument 160 and clears attacking. If no rally point exists it can proceed to attack even below the nominal threshold. An attacking group with four or five members keeps attacking. Attack selection uses the group's average and FindNearestEnemyUnit, then sends mode 3 against the result if nonnull.

FindNearestEnemyUnit (`0x4071f0`) scans nonallied active player roles 1, 2 and 3. It accepts runtime live units except mode 2, runtime 0x8000 or cloak activation bit 4, and minimizes horizontal squared distance. It does not consult the visible cache or independently check sight. Strategic assault destination selection therefore has a different information contract from automatic weapon acquisition.

EscortTimer (`0x4079f0`) moves its whole group to the paired assault's centroid whenever both groups are nonempty. It does not assign each reserve a protected unit or issue a guard mission. SquadScoutTimer (`0x407ae0`) sends groups smaller than five on two or three random points around base, starting with a replace-mode move and appending patrols. If base X and Z are both zero it instead gets the group average and patrols towards the nearest enemy. This branch ignores average failure and dereferences the returned enemy without a null check. Groups of five or more patrol towards a randomly selected map edge, with destination Y zero.

## 9. Spatial/artillery target-area search

SpatialTimer construction and execution are in [ai_player_407d40.cpp](../../../src/ai/ai_player_407d40.cpp) and [ai_player_407e70.cpp](../../../src/ai/ai_player_407e70.cpp). Best position, probe position and initial step all start at map center; bestRating starts zero. On each nonempty-group callback, one time in ten the probe restarts at best and chooses a random horizontal 320-unit step. Otherwise the existing step persists. It advances the probe, conditionally scores it, and retains a new best when RandomInt(newRating) exceeds RandomInt(bestRating). This samples a moving point; it does not calculate an exhaustive optimal firing position.

With mapFlags bit 2, its local visibility helper reads the player's byte sight grid. Despite the local IsExplored name, that grid counts current sight. Otherwise [IsPointVisible](../../../src/ai/ai_player_408090.cpp) (`0x408090`) reads the permanent visibilityMask bit for **g_game->playerIndex**, using the supplied player's dimensions. The latter branch is tied to the global viewing-player index, not the AI timer's player index. Both use projected coordinates X/32 and (Z-Y/2)/32 with bounds rejection.

SumUnitRatingsInRange (`0x40b1c0` in [its file](../../../src/ai/ai_player_40b1c0.cpp)) sums signed tactical definition ratings of cached visible enemies within 160 horizontal world units of the probe. It does not independently recheck readiness. For each group member with flags2 bit 4, a nonzero motion pointer or successful WeaponCanReachPos permits a mode-3 positional order towards best; only a nonzero resolved mission ID is enqueued. Placement, visibility and attackability remain separate tests here.

## 10. Enemy queries and automatic target preference

GetVisibleEnemiesInRadius (`0x40ad80`) appends ready cached visible enemies inside a horizontal radius to a caller vector. It does not clear that vector. When hasSpecial is set and the output remains empty, it appends ready known enemies in radius instead. Existing caller entries suppress that fallback too. The flags argument is unused. HasReadyUnitInRange (`0x40b0d0`) only tests the visible list; it has no known-enemy fallback.

GetFactoriesInRadius (`0x40b530` in [its file](../../../src/ai/ai_player_40b530.cpp)) appends cached friendly candidates still satisfying flags1 bits 6/9, activation bit 1 and horizontal range. It is a service/factory query, not the enemy target collector. All these distance helpers multiply fixed X/Z deltas in 64 bits and take the high 32 bits, yielding squared world distances without a square root.

FindWeaponTarget (`0x40b7b0`) collects candidates using the slot's actual weapon range when useRange is true, otherwise the unit definition range. It samples and removes up to 50 random candidates, so large caches are not exhaustively ranked. Each accepted candidate must be ready, must have definition flags1 bit 15 unless the shooter is an active computer player or matchFlags bit 4 is set, and must pass WeaponCanReachUnit unless the shooter has flags1 bit 28. With useRange false the shooter's overall category bitset additionally rejects matching target types. A weapon flag-7 target-status restriction also applies.

For each accepted unit it rolls a random integer bounded by horizontal distance squared. A lower roll wins within its tier; this biases towards nearer units without making nearest-target selection deterministic. A candidate matching the slot's weapon-category bitset belongs to the fallback tier. The best ordinary-tier target wins whenever one exists, otherwise the best fallback is returned. The category is therefore a preference/fallback distinction in this function, while some callers treat it as a reason to replace an existing target. Those contracts should not be conflated into a universal exclusion rule.

RetargetWeapon (`0x408920`) handles weapon flag 30 by querying targetable projectiles, setting a positional target to the returned projectile representation or clearing the slot. Other weapons only run ordinary selection when runtime bits 0x300000 equal 0x200000, setting or clearing the unit target according to the result. [Weapon runtime](weapons-weapons.md) supplies projectile interception, reach, aim callbacks, firing and damage; acquiring an AI target alone does not guarantee a shot.

RetargetWeapons (`0x4089a0`) spreads work across unit slots using a retained cursor. Each call processes maxUnits/30+1 slots, wrapping at the inclusive player end. A candidate needs a nonzero definition index, exactly zero buildLeft, runtime bit 0x80000000 and the same 0x200000 fire-state pattern. Each of three weapon slots must have flags 2 and 0x10, lack weapon flag 8, and, unless forced, lack command-fire flag 26. Existing targets are discarded for alliance, category match or the flag-7/status-0x10 restriction. It does not independently discard a retained target simply for moving beyond range; the other weapon/reference paths handle their own validity. Computer timers use force=1, allowing command-fire retargeting; the other player path uses force=0.

## 11. Damage reactions, side effects and diagnostics

ReactToAttack (`0x406f80`) first notifies victim references with event 16 and treats an attacker with zero definition index as null. A flags2-bit-12 victim owned by an active computer player postpones manager.nextAction by 30..329 ticks and deletes its orders. This feeds the mobile-builder delay test, rather than globally freezing all AI updates.

For an active role-1/2 victim, a nonallied attacker and completed definition with flags1 bit 16 or 28 permit retaliation. An absent order or order flag 0x20000, overall/primary category acceptance and primary reach allow an attack order. If that does not succeed and the victim has any runtime 0x300000 bit, it considers all three enabled automatic weapon slots, rejects command-fire definitions and unreachable attackers, and replaces an absent, unreachable or category-disfavored current target. Finally it can queue under-attack speech when the order flags lack 0x80 and the recorded attacker/damage-type condition passes. This event path is broader than a periodic AI squad decision.

MarkOwnerNetDirtyFromDamageSplit (`0x406f50`) follows the supplied object's +0x52 pointer if present and sets target bit 6 when a exceeds twice b, otherwise bit 5. It neither clears the alternative bit nor sends a packet itself. The provisional method name is not evidence of a complete networking protocol. FUN_00406f40 is empty. ProbeUnitDefEnergyRate (`0x40ad70`) calls GetEnergyUse and discards the result.

DumpPlayerAI (`0x40c250`) writes tick-derived hours/minutes/seconds, player/controller, terrain/profile, difficulty and every definition's limit, three production ratings, script percentage and names. Its second fprintf uses a preformatted buffer as the format argument. Percent characters originating in names can therefore be interpreted again. The routine also assumes difficulty indexes the three-name array and that the file and player state are valid. It is a diagnostic dump, not save-game serialization.

## 12. Storage support, boundaries and evidence limits

The remaining annotated support comprises the seven timer constructors and seven deleting destructors, the cell copy constructor (`0x40a5b0`), the Unit-pointer vector constructor (`0x40c510`), [vector insertion at 0x408f30](../../../src/ai/ai_player_408f30.cpp), and 30 [container members at 0x40c530..0x40d5b0](../../../src/ai/ai_player_40c530.cpp). Constructors/destructors establish virtual dispatch and owned timer lifetime. Pointer vectors own their storage, not the pointed-to game units. The container members implement size/capacity, resize/insert/erase, destruction, uninitialized copying and filling for pointers, cell records, rating triples, short counts, byte percentages and integer limits. Erase shifts remaining entries; growth allocates and copies elements, invalidating iterators/references into vector storage. Trivial element destruction performs no gameplay cleanup.

The [PlayerAI header](../../../src/ai/player_ai.h) and [SquadManager header](../../../src/ai/squad_manager.h) provide the shared layout. No module entry serializes the full AI object, transmits a dedicated AI snapshot, draws a model or emits particles. Orders, state toggles, weapon targets, speech and reference notifications are its externally visible outputs. Player lifecycle, order dispatch, construction, movement search, sensors and weapon execution provide the downstream behavior.

All 115 address-assigned entries were checked across the source tree, including the out-of-file cache refresh, visibility helper, timer callbacks, scoring and query methods. The boundary excludes the template construction helpers beginning at `0x40d5e0`, assigned to pathfind even though AI containers call them. Policy assets, downloaded definitions and mission parameters determine exact unit preferences and available build menus. Static source establishes the algorithms and original edge cases above; no game execution, build or matching check was used for this documentation.
